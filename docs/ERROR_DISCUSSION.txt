2. UPDATING A PIPELINE
Impl: update_pipeline_definition overwrites the full definition
(snapshot + checkpoint history + back/forward/rollback).

Q: OK with full-overwrite risk? Size ceiling requiring human edit? Want a
diff shown at approval time?
A: -- what else need to be analysed and checked here?

C: Two real gaps: (1) miscasing guard only catches wrong-key-name, not a

click-to-approve time, not buried in chat. Buildable, will build.

10. SP FAILS, SHOWS NO ERROR
Impl: real gap. get_activity_run_error only shows what ADF's control
plane recorded -- if the SP swallows its own exception and returns
"Succeeded," nothing is visible to any tool here. get_activity_run_io is
the only lead (whatever output the SP actually returns).

Q: does the SP return anything inspectable? Same root problem as #7/#8-
silent? Any DB-side audit table a new tool could query?
A: -- we are saying that, when a sp fails it shows no error, what can we
do about that
A: -- we are currently not focusing on these errors, the failed one, for
the no-output the user have a convo with claude and may resolve it
A: -- no
C: Honest answer: given no DB-side audit tables and ADF-only scope,
today there's close to nothing to do -- this is a genuine blind spot, not
a tooling gap. ADF has no visibility into what happens inside the SP
beyond its own return status. Treating as an accepted limitation, not a
build item, unless the SPs themselves are changed to return an explicit
status (a DB-side change, not ours).
